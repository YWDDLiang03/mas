## Gaps to make explicit in the new design

1. **Current activity needs explicit events.** The inspected monitor exposes phase/progress and logged model-call details. For dependable visibility into what is executing now, define agent/tool start, waiting, heartbeat, completion, and failure events; completed-call logs alone are insufficient. The new default UI should present concise action and decision summaries, not require raw model responses.
2. **Progress denominators can change.** The orchestration code changes counts between candidate and later evaluation stages (`orchestration/recommend.py`, lines 621-628 and 670-680). Do not present a stage percentage or linear ETA as an exact measure of total scientific completion. Unknown work should remain visibly indeterminate.
3. **History and semantic differences are separate capabilities.** Existing proposal/review and report snapshots provide a useful history, but the inspected views do not establish a complete field-level diff of all changed parameters and evidence. Design explicit before/after values and links from changes to critiques, sources, and decisions.
4. **Persisted truth must drive status labels.** The loop records `exhausted` without accepting it (`dual_agent/loop.py`, lines 282-300), while the inspected trace API maps that state to `sent_after_revision_limit` (`web/server.py`, lines 983-994). This is a source-level inconsistency to avoid carrying into the new architecture. Define authoritative states and their UI mappings rather than inferring acceptance from a descriptive label.
5. **A readable rationale needs evidence links.** Existing views expose rationale, review concerns, and evidence summaries. The biomedical design should add direct navigation from a decision or version difference to the relevant passage, data, tool result, and expert record, while preserving rejected interpretations and uncertainty.

## Required design behavior for the biomedical MAS

Specify a live run monitor, per-round timeline, version-difference view, candidate detail, evidence inspector, and human-review queue. For every substantive analysis, retain its task context, input/evidence versions, question, responsible actor, timestamps, relevant results, critique, concise decision rationale, outcome, and next action. Distinguish screening rounds, tool retries, human edits, report revisions, and later evidence-refresh runs.

The user should be able to answer: What is happening now? What changed since the previous version? Which evidence caused the change? Who approved it? Which results became stale? Why did the system continue, stop, or abstain? An immutable history with linked corrections should support these answers.

These requirements apply to a single-pass assessment as well as to adaptive multi-round work. More visible rounds are not a success criterion. The next agent should produce detailed architecture, state/interface specifications, and non-executable wireframes; implementation remains a later phase.
